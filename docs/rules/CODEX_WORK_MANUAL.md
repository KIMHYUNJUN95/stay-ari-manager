# Codex Work Manual

## 목적
이 문서는 이 저장소에서 작업할 때 항상 먼저 확인하고 따라야 하는 기본 작업 메뉴얼입니다.
모든 작업은 이 메뉴얼을 먼저 검토한 뒤 시작합니다.

## 핵심 규칙
1. 기존 원본 파일을 수정해야 할 경우, 수정 이유를 먼저 사용자에게 보고하고 명시적인 허락을 받은 뒤 수정합니다.
2. 기존 원본 파일 삭제 권한은 사용자에게 있으며, 허락 없이 절대 삭제하지 않습니다.
3. 빌드, 배포, GitHub 푸시는 사용자 승인 없이 실행하지 않습니다.
4. 디버깅 후 에러, 버그, 기타 문제점이 발견되면 문제점 자체와 그로 인해 발생하는 현상을 사용자에게 먼저 보고합니다.
5. 모든 작업 전 이 메뉴얼을 다시 확인하고 그대로 따릅니다.
6. 기능과 디자인은 항상 고퀄리티, 고급 기능, 성능을 고려해 대기업 수준으로 구현합니다.

## 작업 전 필수 절차
1. 작업 시작 전에 이 메뉴얼을 확인합니다.
2. 요청 사항에 기존 파일 수정, 삭제, 빌드, 배포, 푸시가 포함되는지 먼저 판단합니다.
3. 승인이 필요한 작업이면 이유를 설명한 뒤 사용자 허락 전까지 멈춥니다.
4. 디버깅 중 문제를 발견하면 문제점과 실제 발생 현상을 정리해 먼저 공유합니다.
5. 구현 시 완성도, 성능, 사용성을 우선하여 결과물을 만듭니다.

## 반드시 승인받아야 하는 작업
- 기존 원본 파일 수정
- 기존 원본 파일 또는 리소스 삭제
- 빌드 실행
- 배포 실행
- GitHub 푸시

## 문제 보고 기준
- 어떤 문제인지 명확하게 설명할 것
- 그 문제 때문에 어떤 현상이 생기는지 함께 설명할 것
- 승인된 후속 수정 전, 먼저 사용자에게 공유할 것

## 품질 기준
- 엔터프라이즈급 완성도를 목표로 작업합니다.
- UI/UX, 기능 깊이, 성능, 디테일 품질을 함께 고려합니다.
- 단순 동작만 하는 낮은 완성도의 구현보다, 가능한 범위 내에서 더 고급스럽고 안정적인 구현을 우선합니다.

## 파일 안전성 및 손상 방지 규칙
- 인코딩 깨짐, BOM 변형, 줄바꿈 형식 변경, JSON 인덱스 파일 손상 같은 리스크를 항상 먼저 고려합니다.
- 기존 파일 수정 시 필요한 최소 구간만 수정하고, 파일 전체 재작성이나 대규모 일괄 치환은 원칙적으로 금지합니다.
- 주석, 문자열, 라벨, 다국어 텍스트가 많은 파일은 인코딩 리스크가 높은 파일로 간주하고 특히 더 보수적으로 다룹니다.
- 인코딩이 이미 깨져 있거나 깨질 가능성이 높은 파일은 먼저 위험성과 예상 현상을 사용자에게 알린 뒤 최소 수정만 수행합니다.
- 기존 파일의 인코딩, BOM, 줄바꿈 형식은 특별한 이유가 없으면 유지합니다.
- 내용 수정과 무관한 포맷 변경, 공백 정리, 정렬 변경, 자동 포맷팅 전체 적용은 금지합니다.
- JSON, TOML, 인덱스 정의 파일, 설정 파일은 구조 손상 위험이 큰 파일로 간주하고 필요한 키만 최소 수정합니다.
- `firestore.indexes.json`, `firebase.json`, `package.json`, 잠금 파일, 배포 설정 파일은 변경 전후 구조를 반드시 다시 확인합니다.
- 문자열 깨짐 수정 작업 중에는 디자인, 레이아웃, 기능 로직까지 같이 바꾸지 말고 화면에 실제로 보이는 손상만 분리해서 다룹니다.
- 새 문자열 추가 시에는 가능하면 ASCII를 우선 사용하고, 비 ASCII 문자가 꼭 필요할 때만 기존 파일 관례를 확인한 뒤 사용합니다.
- 대형 파일이나 고위험 파일을 수정한 뒤에는 파싱, 빌드, 관련 범위 diff를 통해 손상 여부를 반드시 확인합니다.
- 한 번의 수정으로 위험이 커질 경우 여러 작은 패치로 나누어 적용하고, 예상치 못한 문자열/레이아웃 변화가 보이면 즉시 멈추고 사용자와 다시 맞춥니다.
